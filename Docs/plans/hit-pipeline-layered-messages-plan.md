## Binding design rules — THE LAYERED MODEL (Einar's, settled at plan review; **amended 2026-07-16**, see Amendments above)

**Two idioms, one criterion:**
- **Fan-out context** (many arbitrary systems respond to one event, open responder set) → a **message** over ExecuteEvents. "Hit" is the archetype: 5 unrelated responders. **Promotion criterion (R2) — four clauses, ALL required:** a context earns a message at **(1) ≥2 unrelated responders**, that are **(2) on the dispatch target's own GameObject**, **(3) on the same peer**, and **(4) served synchronously**. When an operation's responders multiply, promote it then — pull, never push.
  - **Cross-peer fan-out rides the replicated SyncVar `OnChange` (ADR 0004), NEVER a message.** ExecuteEvents is an in-process call; it cannot cross the wire. A message dispatched from a `[Server]`-only path reaches no client.
  - **Off-hierarchy fan-out stays a C# event or a `MatchMediator` wire.** `ExecuteEvents.Execute` calls `GetComponents` on exactly ONE GameObject; `ExecuteHierarchy` walks UP only (and is not used here). A C# event is *reference*-scoped and reaches a child, a parent, a canvas, or another scene; a message is *GameObject*-scoped. For a responder set deliberately scattered by concern, GameObject-scoping is the worse addressing model.
- **Operation** (one component's capability, many callers) → **direct coupling: GetComponent + public method call.** A message with a known singular receiver is a misuse of dispatch. Damage/knockback/hitstun *delivery to the victim* are operations, NOT messages.

**Layers are vocabulary, not a budget** (amended 2026-07-16 — the depth bound and R1 are **DELETED**):
- Layer 1: the context (`HitMessage`), dispatched at a site. Layer 2: handlers (`IHitMessageHandler` implementors) — MAY GetComponent (own GO or others, incl. `GetComponentInParent` on the victim) and call public methods. Layer 3: the public operations they call (`ApplyImpulse`, `ApplyHitstun`, `TakeDamage`).
- These name **roles within one dispatch**, not a global depth budget. **Any layer may dispatch a new context — this is not restricted.** The on-hit explosion this plan already anticipates (see the extraction trigger: "a second hit source (explosion over N victims, a cast)") IS a layer-2 dispatch, and `NestedDispatchPoolProbe` already tests nested dispatch. A rule forbidding what the plan tests for is a bad rule.
- **What the deleted bound was protecting is bought better elsewhere.** Analyzability comes from the **typed message** — grep every dispatch site, every implementor — not from depth arithmetic. A 5-deep chain of typed contexts is more analyzable than a 2-deep chain of untyped behaviour calls; the bound was scaffolding for a property the message type already guarantees.
- **The residual risk is CYCLES, not depth** (`X → Y → X`: stack overflow + pooled-message aliasing). Doctrine cannot catch that, so it is guarded at runtime instead of by a rule: **`ServerCollision.DispatchHit` keeps a re-entrancy depth counter that logs an error past a sane bound (8) under `UNITY_EDITOR || DEVELOPMENT_BUILD`**, compiled out of release. A guard, not a law.

**Carried rules:**
1. A message/operation input feeds a **recompute**, never an in-place edit of an effective value. Controllers keep (authored baseline, registries); removal = delete + recompute; `ResetState` clears registries, never baselines.
2. Consume-once data integrates at the **tick boundary** — `PawnMovement.PendingImpulses` stays a PUBLIC Family-A contribution surface (PawnMovement is now UNTOUCHED by this migration); `ApplyImpulse` ends in `movement.PendingImpulses.Add(...)`, a legal layer-3 data contribution.
3. `HitMessage` derives `BaseEventData`, `base(null)` (safe — verified in ugui 2.0.0 source), **pooled via static Get/Release on HitMessage itself** (only one pooled type — MessagePool<T> failed the inline rule), `Reset()` nulls every ref, Release immediately after dispatch; `HitMessage.Functor` statically cached with the channel guard baked in.
4. All gameplay mutation originates `[Server]`; the KnockbackController TargetRpc hop to the owning client (client-simulated movement) is the sanctioned delivery leg, identical to today.
5. Hit atomicity by construction: durability spent FIRST in `ServerCollision.DispatchHit`, then every handler runs unconditionally (even on a dead projectile); death gates only despawn/projectile-channel afterwards. Victim-side delivery is plain synchronous layer-2/3 calls — same proof status as today. ExecuteEvents' per-handler try/catch strengthens this.
6. Disabled component = silent (ExecuteEvents checks `isActiveAndEnabled`) — this IS the composability/strip hook; `ResetState` re-enables (`enabled = true`). NOTE: ExecuteHierarchy is no longer used anywhere (victim resolution = GetComponentInParent) — the reentrancy risk and its pins are DELETED from this plan.

## ADR 0005 (skeleton in Docs/design/0005-hit-pipeline-layered-messages.md)

_Draft content; all 2026-07-16 amendments are Einar-approved and folded in below._

**The decision IS the layered model**: (a) the two-idiom criterion — a fan-out context earns an ExecuteEvents message at **≥2 unrelated responders, same-GameObject, same-peer, synchronous (all four clauses)**; a single-receiver operation is a direct call; **cross-peer fan-out rides SyncVar `OnChange` (ADR 0004) and off-hierarchy fan-out stays a C# event / `MatchMediator` wire** — neither is ever a message; (b) **layers are vocabulary, not a depth budget — any layer may dispatch, and cycles are caught by a runtime re-entrancy guard rather than a rule** (the depth bound was vacuous as written, and any binding repair forbade this plan's own explosion extraction trigger); (c) merged per-datum controllers, under a **named `<X>Controller` rule — a controller OWNS STATE and exposes an API to modify it, and is the state-owning half of the dispatch model (messages fan out; controllers hold state and expose the operations handlers call)**; it excludes `Damage` (no mutation API) and renames `Health` → `HealthController`, resolving the `Pawn.Health`-the-value vs `Health`-the-component collision; (d) the hit sequence inline in `ServerCollision.DispatchHit` with the named extraction trigger (second hit source extracts, never duplicates).

Alternatives rejected: incumbent kept (hand-rolled handler harvest; every new exchange edits the resolver); messages-everywhere (victim-side single-receiver messages are dispatch theater — 4 message types + a generic pool deleted from the plan's own first draft); split components (no single home per datum); **a damage/DamageTaken context** (2026-07-16 — real fan-out, but `CurrentHealth.OnChange` is already a cross-peer, engine-native, zero-cost dispatcher at the correct site with per-subscriber filtering; the message idiom cannot beat it by wrapping it, reaches 0-of-4 responders, and collects a zero offset — the responders share a signal, not a predicate); **a BLANKET `XController` rename** (2026-07-16 — rejected as a suffix applied on sight; the `<X>Controller` *rule* adopted in its place is a definition with exclusions, which is a different thing: it rules `Damage` out and `HealthController` in on stated grounds).

Accepted trades: dormant halves on pooled bullets (conditional SyncVar reset, no ticks); disabled=silent as the strip hook; ugui as gameplay dependency; contact damage still on IDamageable (future slice); **the idiom's honest reach is two instances (Hit, SpawnBuff-when-triggered) — rule-of-two, barely met, recorded rather than hidden.**

**Pay-down receipt: HitResolver + HitContext + IHitHandler + four components deleted; a hand-rolled harvest replaced by engine-maintained dispatch. The model itself also shrank at review — the depth bound and R1 deleted, not added to.**

**Consequences worth recording:** the pawn's cosmetic responders are **scattered across child GOs by concern** (`PawnColor` on `Body Mesh`, `PawnDamageVfx` on `VFX`) — any future "just dispatch it on the pawn" instinct hits this wall, because `ExecuteEvents` is GameObject-scoped while a C# event is reference-scoped. **By this ADR's own criterion, `LocalUIEvents` is 14 channels of single-receiver dispatch (13 with exactly one subscriber, 1 dead) — the largest pay-down target the criterion names, and it is NOT addressed here.**

**Register append** (supersession named inline): `2026-07-16 · Constantine/Parnas — cross-component gameplay coupling follows the LAYERED MODEL: a fan-out context earns a pooled ExecuteEvents message only at ≥2 unrelated responders that are same-GameObject, same-peer, and synchronously served (all four clauses — the one-clause form was calibrated on N=1 and greenlights peer-disjoint promotions that break silently, e.g. PawnManager.OnPawnKilled); cross-peer fan-out rides SyncVar OnChange (ADR 0004); off-hierarchy fan-out stays a C# event or a MatchMediator wire; a single-receiver operation is a direct call. Layers are vocabulary, not a depth budget: ANY layer may dispatch, and cycles are caught by a runtime re-entrancy guard, not doctrine. Supersedes "never call a sibling's behaviour" (now: legal, and typed at the dispatch); ADR 0005.`

**Second register append** (the naming rule — Einar's, and it closes a gap the dispatch model left): `2026-07-16 · Parnas/Dijkstra — a component named <X>Controller OWNS STATE and exposes an API to modify it; controllers are the state-owning half of the messaging/dispatch pattern (messages fan out; controllers hold the state and expose the operations handlers call). The rule is predictive because it EXCLUDES: Damage keeps its name (state but no mutation API — its presence is the switch), Pawn<X> shells keep the CLAUDE.md Pawn<X>/<X>Processor pairing, and NetworkUIController is thereby known-misnamed (a bridge owning no modifiable state — rename pending). Health → HealthController, which also resolves Pawn.cs's use of one word for two things (Health the component vs Pawn.Health the SyncVar value). Supersedes the earlier "no XController convention" recommendation, which was aimed at a blanket suffix and measured Controller as-used-in-the-wild rather than as-defined; ADR 0005.`

**Skill updates**: presence-dispatch (IHitMessageHandler, guard in `HitMessage.Functor`, hit sequence in `ServerCollision.DispatchHit` + extraction trigger; disabled=silent strip hook; order-independence pinned; "we own no dispatch machinery" now literally true — one message type + one pool, zero dispatch classes); cross-component-communication (**the governing rule is replaced by the layered model**: Family A/B survive as the data terminals and notification family; hit-exchange paragraph → controllers with two registries, direct calls; the old `ApplyImpulse` unnamed exception is retired by naming; **add the four-clause R2 and its two escape hatches — cross-peer → SyncVar `OnChange`, off-hierarchy → C# event / MatchMediator — since those are what stop R2 greenlighting a silent peer-disjoint break**; Family B is NOT deprecated by the message idiom — it remains correct for every off-hierarchy and cross-peer fan-out, which is most of them).
