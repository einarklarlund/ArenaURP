# AI-development practices register

The ledger that makes "continually evolve and re-evaluate" real instead of a vibe. Every AI-dev practice we have considered is here with a **status**, a **date**, a **rationale**, and a **re-eval-by** date. Without this, adopted practices silently rot and rejected ones get re-litigated.

Statuses: **Adopted** · **Partially adopted** · **Watching** (promising, not yet worth the cost) · **Rejected** (with reason) · **Superseded**.

Maintained under the [[workflow-artifacts]] skill. The `habit-check` hook nudges a re-evaluation every 20 substantive tasks; the frontier-scan practice below says to also scan for *new* practices, not only re-judge old ones.

## Sourcing standard (non-negotiable for anything in this table)

Every practice claim must be traceable to **who** advocates it and **why they are credible** — the user reads sources, not vibes. Record, per practice: **Advocate** (person/org), **Authority** (their credential/track record), **Source** (link), **Confidence tier**:

1. **First-party** — Anthropic docs (`code.claude.com/docs`), official changelog. Authoritative on what the tool *does*.
2. **Named practitioner** — an identifiable engineer/team with a track record, writing from real use. Credible on what *works in practice*; still verify against tier 1.
3. **Community/aggregator** — blogs, marketplaces, SEO content (7tonshark, sitepoint, mindstudio, lobehub, etc.). A **lead to investigate, never a citation to rely on.** Verify before adoption.
4. **Unattributed** — no named author. Not admissible; find the primary source or drop it.

**Honesty note (self-critique):** the "Watching" rows above (eval harness, grading agent, fallback chains) were researched via web search that returned mostly **tier-3** sources; only the Claude Code capability facts are tier-1. Treat those rows as *leads*, not endorsements — re-source to tier 1–2 before any of them moves to Adopted. When researching, use the `claude-code-guide` agent for tier-1 facts and demand a named advocate for any practice claim; it has itself been wrong (statusline, the UserPromptSubmit field name), so verify it too.

## The re-evaluation ritual (when the cadence fires, or on demand)

1. **Re-judge one Adopted practice.** Is it still earning its keep, or has it become wallpaper / cruft? Downgrade or delete honestly — a dead practice is worse than none.
2. **Advance one Watching practice.** Has the trigger arrived? Run a small trial, then Adopt or Reject with a reason.
3. **Scan for one NEW practice** against current best practice (use the `claude-code-guide` agent — verify, don't assert; it has been wrong before). Add it as Watching with a trigger.
4. Stamp the date. Prune Superseded rows to keep the table legible.

Anti-cruft rule applies to practices as to code and interfaces: **earn each adoption with a real need, and write the originating need into the row.** Propose the rest as Watching and let the user choose.
