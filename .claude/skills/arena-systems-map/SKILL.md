# Arena systems map

One governing idea: **a server-authoritative simulation whose logic lives in pure, EditMode-tested cores.** Every decision below is a consequence, and each has a skill with the detailed rules.

## The decisions

1. **Server-authoritative over FishNet.** The server is the single source of truth; clients send intent and observe synced results. Send nothing a peer can derive or look up — identity in, state looked up. → [[fishnet-conventions]]
2. **Functional core, imperative shell.** Gameplay logic lives in pure `Arena.<X>.Core` processors (`Process(state, in config, in input, dt) → newState`); the `Pawn<X>` MonoBehaviour is a thin shell that builds the input struct, calls the processor, applies the result. Query results go in as data, effects come out as data — never an injected `IWorld`. → [[functional-core-imperative-shell]]
3. **Few communication mechanisms.** Systems influence each other through producer-owned contribution lists folded per tick (modifiers, impulses) or notifications (events, SyncVar.OnChange, the MatchMediator) — and we actively consolidate rather than invent new channels. → [[cross-component-communication]]
4. **Kinds are identity-only type objects.** A projectile/ability *kind* is an empty ScriptableObject (name, icon, `InstancePrefab`) plus its own prefab copy; all gameplay config is authored on the prefab's generic components, so every peer has it locally and nothing rides the wire. Instances self-initialize on every peer — that's what makes client-predicted spawn correct. → [[type-object-pattern]]
5. **Behaviour is composed from components discovered by presence.** Swappable behaviour is a component you attach, not an authored operation list: a hit reaction is an `IHitHandler` component filtered by hit channel (the call site), an ability's spawn is a `SpawnNetworkObjects` component — the site finds them with `GetComponents`. Varies-in-data (stat / on-spawn buffs) is an authored struct. Engine-native composition, no owned dispatch machinery (ADR 0003). → [[presence-dispatch]]
6. **Every networked change gets a PlayMode test; everything else gets the cheapest test that catches it.** → [[integration-testing]]

## The game in those terms

**A player** is a `NetworkPlayer` (SyncVars: `Username`, `IsReady`, `Score`, `ControlledPawn`, `RespawnTimeEnd`; `IsBot` is a plain server-side field) controlling a **Pawn**. The pawn prefab is a composition of thin shells — `PawnMovement`, `PawnWeapon`, `PawnTemperature`, `PawnColor`, `PawnInteraction` — each delegating to its pure processor, plus the hit-RECEIVING components on the root (`Health`, `KnockbackReceiver`, `HitstunReceiver`). One `PawnInput` base with `HumanPawnInput` / `BotPawnInput` / `ScriptedPawnInput` behind it means humans, bots, and tests drive the identical prefab (decision 2; every updater early-outs on `!input.IsActive`). Health is the one generic `Health` component (the sole `IDamageable`, used by pawns, bullets, and props alike); `Pawn` is a thin facade over it.

**Cross-pawn influence** is decision 3: `PawnTemperature`, `PawnMovementEffects`, and `PawnPassiveAbilities` contribute `MovementModifier`/`WeaponModifier` structs into `PawnMovement.Modifiers`/`PawnWeapon.Modifiers`, folded by the processors every tick (neutral identity = absent contributor changes nothing); `KnockbackReceiver` pushes consume-once impulses into `PendingImpulses`. **A hit** lands via three independent DEALER→RECEIVER exchanges sharing one shape — damage, knockback, hitstun — fired from component presence at the hit site by `HitResolver` — no courier effect — with each end folding its own modifiers (see CLAUDE.md "hit exchange"; [[presence-dispatch]] for the handler + exchange model).

**A projectile** is decisions 4+5+1 together. A kind is an empty `ProjectileType` + its own prefab copy carrying: `NetworkedMotion` (closed-form deterministic motion ticked independently on every peer — only the per-spawn anchor of tick/origin/direction rides the spawn payload), `ServerCollision` (server-only sphere-casts, classifies hits via the pure `ServerCollisionProcessor`, then resolves each hit through `HitResolver`'s per-channel entry point (`ResolveSurfaceHit`/`ResolvePlayerHit`/`ResolveProjectileHit`) — the presence-based exchanges, the durability spend, and the `IHitHandler` reactions discovered on the projectile then on the owner, all in ONE atomic hit even if the projectile dies mid-hit), `Health` (durability), `Damage`. Spawning is the inline three-step at each site: `GetPooledInstantiated` → stamp `NetPlayerOwnership.SpawnOwnerId` → `ServerManager.Spawn` (sites: `PawnWeapon.ExecuteShot`, the `SpawnNetworkObjects` component on an active ability). The owner's ability contributions are never payloaded — the server looks them up from the owner id at hit time; per-peer on-spawn buffs are applied by `SpawnBuffReceiver` from the replicated passives.

**A match** is decision 3 at manager scale. `MatchFlowManager.State` is a `SyncVar<MatchState>` (`Pregame → PregameCountdown → During → PostgameCountdown → Postgame`); `DeathmatchManager` owns score/win; `PawnManager` owns spawn/respawn; `NetworkPlayerManager` owns the roster. They never reference each other — `MatchMediator` is the single wiring point that subscribes them together. UI hears about it via `NetworkUIEvents`/`LocalUIEvents` (static buses, both with `Reset()`).

**Abilities** are decisions 4+5. Granting one spawns its kind's prefab and parents it under the pawn's NetworkObject via `NetworkObject.SetParent` (never raw transform parenting — only SetParent replicates). **Actives** (`PawnActiveAbilities`): a `SyncList<ActiveAbility>` roster for slot order + HUD — ordering is load-bearing: *Spawn before Add, RemoveAt before Despawn*; using one runs the instance's `SpawnNetworkObjects` components (`ActiveAbility.ServerUse`, aimed from the caster). **Passives** (`PawnPassiveAbilities`): no roster — membership is derived from the replicated child instances; each `PassiveAbility` carries plain `MovementBuff`/`WeaponBuff` struct data (standing modifier contributions, re-derived on every roster change) plus contributed hit reactions (`IHitHandler` components harvested at the owner's hit site via `CollectHitHandlers`) and a `SpawnBuff` (`SpawnModifier` struct — per-peer speed/scale/max-health transforms of just-spawned owned objects).

## Open design questions (don't improvise these)

- **How runtime buffs reach a projectile's damage** — the hit pipeline reads the dealer's base `Damage.Amount` only (`HitResolver` carries an unused per-target `damageMultiplier` slot as the seam). This is the NEXT DESIGN TASK; candidates: a `Damage.Modifiers` contribution list (Family A) vs. a context-carried contribution. Design it in a dedicated session, not as a side effect of another feature.
- **Debuffs** — there is no debuff system yet (the old `ApplyDebuff` stub was deleted with ADR 0002).
- **Ammo** — stubbed (`HasAmmo = true`); `AmmoPerFire` config exists but is not consumed.
