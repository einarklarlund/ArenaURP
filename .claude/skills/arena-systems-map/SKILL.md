# Arena systems map

One governing idea: **a server-authoritative simulation assembled from components, with determinism-critical and branchy logic isolated in pure, EditMode-tested cores.** Every decision below is a consequence, and each has a skill with the detailed rules.

## The decisions

1. **Server-authoritative over FishNet.** The server is the single source of truth; clients send intent and observe synced results. Send nothing a peer can derive or look up — identity in, state looked up. → [[fishnet-conventions]]
2. **Components are the primary unit; pure cores are a targeted exception.** Logic lives in the component (MonoBehaviour composition) by default — generic-via-config, flat hierarchy. Determinism-critical or heavily-branchy logic is extracted into a pure `Arena.<X>.Core` processor (`Process(state, in config, in input, dt) → newState`) with an EditMode test: query results go in as data, effects come out as data — never an injected `IWorld`. Reuse is not a reason to extract; silent-desync / branchy-decision test-isolation is (ADR 0008). → [[component-design]]
3. **Few communication mechanisms.** Systems influence each other through producer-owned contribution lists folded per tick (modifiers, impulses) or notifications (events, SyncVar.OnChange, the MatchMediator) — and we actively consolidate rather than invent new channels. → [[cross-component-communication]]
4. **Kinds are identity-only type objects.** A projectile/ability *kind* is an empty ScriptableObject (name, icon, `InstancePrefab`) plus its own prefab copy; all gameplay config is authored on the prefab's generic components, so every peer has it locally and nothing rides the wire. Instances self-initialize on every peer — that's what makes client-predicted spawn correct. → [[type-object-pattern]]
5. **Behaviour is composed from components discovered by presence.** Swappable behaviour is a component you attach, not an authored operation list: a hit reaction is an `IHitMessageHandler` component filtered by its `EnabledHitChannels`, an ability's spawn is a `SpawnNetworkObjects` component — the site finds them with `GetComponents`. Varies-in-data (stat / on-spawn buffs) is an authored struct. Engine-native composition, no owned dispatch machinery (ADR 0003/0005). → [[presence-dispatch]]
6. **Every networked change gets a PlayMode test; everything else gets the cheapest test that catches it.** → [[integration-testing]]

## The game in those terms

**A player** is a `NetworkPlayer` (SyncVars: `Username`, `IsReady`, `Score`, `ControlledPawn`, `RespawnTimeEnd`; `IsBot` is a plain server-side field) controlling a **Pawn**. The pawn prefab is a composition of thin shells — `PawnMovement`, `PawnWeapon`, `PawnTemperature`, `PawnColor`, `PawnInteraction` — each delegating to its pure processor, plus the per-datum controllers on the root that hold the hit-RECEIVING half (`HealthController`, `KnockbackController`, `HitstunController`). One `PawnInput` base with `HumanPawnInput` / `BotPawnInput` / `ScriptedPawnInput` behind it means humans, bots, and tests drive the identical prefab (decision 2; every updater early-outs on `!input.IsActive`). Health is the one generic `HealthController` component (the sole `IDamageable`, used by pawns, bullets, and props alike); `Pawn` is a thin facade over it.

**Cross-pawn influence** is decision 3: `PawnTemperature`, `PawnMovementEffects`, and the owner's applied `MovementPassive`/`WeaponPassive` (added at pawn spawn via `PawnPassiveLoadout`) contribute `MovementModifier`/`WeaponModifier` structs into `PawnMovement.Modifiers`/`PawnWeapon.Modifiers`, folded by the processors every tick (neutral identity = absent contributor changes nothing); `KnockbackController` pushes consume-once impulses into `PendingImpulses`. **A hit** is one typed `HitMessage` dispatched (`HitMessage.Dispatch`) to every `IHitMessageHandler` on the source; damage, knockback, and hitstun are per-datum controllers whose dealer half responds and calls the victim's controller directly — no courier effect, no dispatch class — each end folding its own modifiers (see CLAUDE.md "hit"; [[presence-dispatch]] for the message + controller model; ADR 0005).

**A projectile** is decisions 4+5+1 together. A kind is an empty `ProjectileType` + its own prefab copy carrying: `NetworkedMotion` (closed-form deterministic motion ticked independently on every peer — only the per-spawn anchor of tick/origin/direction rides the spawn payload), `ServerCollision` (server-only sphere-casts, classifies hits via the pure `ServerCollisionProcessor`, then builds a pooled `HitMessage` and calls `HitMessage.Dispatch` — durability spent FIRST, then every `IHitMessageHandler` on the source in component order, channel-filtered, all in ONE atomic hit even if the projectile dies mid-hit), `HealthController` (durability), `DamageController`. Spawning is the inline three-step at each site: `GetPooledInstantiated` → stamp `NetPlayerOwnership.SpawnOwnerId` → `ServerManager.Spawn` (sites: `PawnWeapon.ExecuteShot`, the `SpawnNetworkObjects` component on an active ability). The owner's ability contributions are never payloaded — a passive self-clones its handler onto the owner's projectiles at spawn (`IOwnedObjectContribution` via `SpawnContributionReceiver`), so by hit time they are ordinary handlers on the source; per-peer on-spawn buffs are applied by the same `SpawnContributionReceiver` from the replicated passives.

**A match** is decision 3 at manager scale. `MatchFlowManager.State` is a `SyncVar<MatchState>` (`Pregame → PregameCountdown → During → PostgameCountdown → Postgame`); `DeathmatchManager` owns score/win; `PawnManager` owns spawn/respawn; `NetworkPlayerManager` owns the roster. They never reference each other — `MatchMediator` is the single wiring point that subscribes them together. UI hears about it via `NetworkUIEvents`/`LocalUIEvents` (static buses, both with `Reset()`).

**Abilities** are decisions 4+5. Granting an **active** spawns its kind's prefab and parents it under the pawn's NetworkObject via `NetworkObject.SetParent` (never raw transform parenting — only SetParent replicates); passives are ref-adds to a loadout, no spawn (below). **Actives** (`PawnActiveAbilities`): a `SyncList<ActiveAbility>` roster for slot order + HUD — ordering is load-bearing: *Spawn before Add, RemoveAt before Despawn*; using one runs the instance's `SpawnNetworkObjects` components (`ActiveAbility.ServerUse`, aimed from the caster). **Passives** (ADR 0009): NOT spawned per player. A KIND is authored once as a nested-`NetworkObject` child of a shared `PassiveRegistry` (one root NObj spawned per match by `MatchMediator`, globally observed); each player's `PlayerPassiveLoadout` on `NetworkPlayer` holds a `SyncList<NetworkObject>` of refs to those KINDs (grant = add a ref, remove = remove, **steal = move a ref** — no spawn/despawn, foreign-HUD-readable, per-game persistent). A KIND = a `PassiveInfo` (identity) + one or more `Passive` applicators, each coupled to the ONE component it configures (`MovementPassive`→`PawnMovement`, `WeaponPassive`→`PawnWeapon`, `SpeedPassive`→`NetworkedMotion`, `ScalePassive`→`SpawnScale`, `CollisionRadiusPassive`→`ServerCollision`, `MaxHealthPassive`→`HealthController`), plus any `IOwnedObjectContribution` on-hit controllers. Application is target-driven and one-shot: a pawn applies its owner's loadout at spawn (`PawnPassiveLoadout`), a spawned object at spawn (`SpawnContributionReceiver`); `CanApplyTo` (component presence) decides which passives act on a given target.

## Open design questions (don't improvise these)

- **How runtime buffs reach a projectile's damage** — the hit pipeline reads the dealer's base `DamageController.Amount` only; the controllers' `OutgoingModifiers` registries exist but have no contributors, and the old per-target `damageMultiplier` slot died with `HitResolver` (ADR 0005) — a per-target multiplier must be re-established, not filled. This is the NEXT DESIGN TASK; candidates: a standing `OutgoingModifiers` contribution vs. an on-spawn multiplier vs. a per-target field on `HitMessage`. Design it in a dedicated session, not as a side effect of another feature.
- **Debuffs** — there is no debuff system yet (the old `ApplyDebuff` stub was deleted with ADR 0002).
- **Ammo** — stubbed (`HasAmmo = true`); `AmmoPerFire` config exists but is not consumed.
