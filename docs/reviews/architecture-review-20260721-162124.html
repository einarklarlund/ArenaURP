Architecture review — ArenaURP

2026-07-21 · deepening opportunities

The verdict first: this codebase is architecturally healthy. The pure-core pattern (ADR 0008) produces genuinely deep modules where it lands — NetworkedMotion, the *Processor cores, MatchMediator — and the presence-dispatch, per-datum-controller, and type-object patterns are all working as their ADRs intend. What follows is a small, targeted set of friction points, not a rescue. Nothing here re-litigates a settled ADR without saying so.

One theme connects half of these

The extraction reflex points at the safe complexity. Trivial arithmetic gets lifted into a testable core (AbilityInventoryLogic, HealthState.Fraction) while the risky logic — network apply-timing, per-spawn buff reseed, death transitions — stays in the NetworkBehaviour shell, reachable only through PlayMode. The core buys confidence disproportionate to the risk it covers. Several candidates below are the same inversion in different clothes.

Four concretions of the seam clear rule-of-two. Variation moves into authored config — the project's generic-via-config ideal.

Problem
Four modules whose interface all but equals their implementation, kept apart only by an absent shared seam.

Solution
An IScalarBuffTarget (read Multiplier, ApplyMultiplier) on the four targets; one config-driven passive that selects its seam.

  • Delete 3 shallow modules

ADR 0009 nuance — the ADR blesses "one component instance per seam," not one hand-written class per seam; the four-way class duplication is not ADR-recorded. Honest caveat: one object can host several seams, so the config must name which — that selector is the load-bearing design choice for the grilling loop.

4 · Resolve the Health core inversion — deepen it or delete it

Worth exploring in-process

Combat/HealthController.cs · Health/HealthState.cs

Before · the core covers the wrong half

HealthState.FractionEditMode ✓
— shell, PlayMode-only —

The tested core is a one-line divide-by-zero guard. The bug-prone reseed/clamp/death logic sits in red — untested.

After · two honest paths

a · deepen

Core owns Seed/Loss/Heal/BuffMax as pure transitions returning new state; shell only applies + syncs → EditMode reaches the risk.

b · delete

If it's "just a clamp," inline HealthState — ADR 0008's own rule: a clamp is not worth a pure core.

Problem
The pure core holds a one-line guard while the seed/buff/death logic — the actual failure surface — lives untested in the shell.

Solution
Decide (a) vs (b) against ADR 0008's own criterion. The decision is the work — grilling territory.

ADR 0008 arbitrates its own rule — "extract a pure core only when determinism-critical or heavily branchy." A max-health buff that reseeds SyncVars across pooled reuse is at least arguable on both counts; a clamp is neither. This isn't re-litigating 0008 — it's applying it to a module that drifted from it.

One 5-screen concept, four representations, three translation tables. UIStateMapper owns only 3 of ~12 visibility decisions; the rest is flat wiring here.

Problem
The machinery exceeds the depth it delivers — to answer "why is screen X up?" you consult the mapper and 14 hardcoded wires and the raising view.

Solution
Let one table own state→view; collapse the redundant ViewKind/Type hops.

  • Fewer representations of one concept
  • Locality: visibility authority concentrates
  • Interface shrinks toward its real depth
Structural floor — the Core-assembly split forces the MatchState↔UIMatchState mirror (a Core enum can't see the engine enum). That one hop stays; the other two are the collapsible redundancy.

1 · Collapse the scalar-multiplier passives

It is the truest deepening on the list and the best-aligned with the project's own north star: four shallow modules become one config-driven module behind an earned seam — the generic-via-config ideal, with the rule-of-two decisively cleared (four concretions). It deletes code, shrinks the interface, and lays exactly the seam the deferred damage-buff channel in DESIGN.md will reuse.
