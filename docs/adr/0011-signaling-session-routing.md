# ADR 0011 — Bidirectional trickle routes through server-owned signaling sessions

- **Status:** Accepted (2026-07-24)
- **Date:** 2026-07-24

Trickle must flow host→client *and* client→host, but the signal server could only route client→host (it rewrites the connection id from a map keyed on the offer, `SignalServer.js:166`), and that rewrite is also the anti-spoof guarantee that a client can't inject candidates into another player's connection. So the server now owns a **signaling session** — an authoritative (host, client, connectionId) record minted at `attemptToJoinRoom`, named on the wire by an **opaque server-minted token** handed to both peers in messages already in flight (no extra round trip), with sender identity stamped by socket. Direction is carried by the opcode (`trickleToClient` / `trickleToHost`) so a host-as-client loopback and multi-role peers route unambiguously; the session is scoped to one attempt and swept at establish-or-fail, but its **token ID space is built now** so a future host-minted reconnect/reclaim can re-open a route to an existing `connectionId` without rework. We rejected a pure dumb relay (deletes the anti-spoof guarantee, forcing per-message host validation) and a long-lived/Redis-persisted session (a signaling session identifies *sockets*, dies on a WebGL page reload, and would make the relay co-authoritative over player identity against our server-authoritative model — reconnect identity must be host-minted).

Considered options: server-owned per-attempt session + token (chosen) · keep the client→host rewrite + a second reverse map (rejected — two routing models for one concept) · pure dumb relay (rejected — security regression) · long-lived / Redis session (rejected — wrong authority, fails on reload). Cross-repo contract; see the signal-server side in ArenaInfra's ADR + plan.
